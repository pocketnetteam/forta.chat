# Аудит сборки (Vite) и холодного старта

**Дата:** 2026-08-13
**Контекст:** проект использует **Vite**, не Webpack (см. `vite.config.ts`, `package.json`). Ниже — аудит `vite.config.ts`, `index.html` и цепочки загрузки скриптов, с конкретными цифрами из `dist/` после `npm run build`, и приоритизированный список фиксов под холодный старт на Android (minSdk 24).

## TL;DR

На холодном старте (первый заход, пустой кэш) до интерактивного первого кадра браузер должен скачать и распарсить **~4.1 МБ gzip** JS. Из них **~3.5 МБ (81%)** — это Matrix SDK (`matrix-js-sdk-bastyon`), который **грузится eager'но на любом экране**, включая `/welcome` и `/login`, где он ещё не нужен. Это самый крупный рычаг из всех найденных.

Второй по значимости — цепочка из 13 legacy-скриптов (`public/js/lib/...`) грузится **последовательно** (`await` в цикле), а не параллельно, что на мобильной сети/Tor превращается в 2-4 секунды чистой сетевой задержки поверх ~310 КБ gzip полезной нагрузки.

Оба фикса — точечные, без архитектурного рефакторинга (см. project constraint "только фикс/оптимизация").

## P0 — критично для холодного старта

### 1. Matrix SDK (9.4 МБ / 3.46 МБ gzip) грузится eager на КАЖДОМ экране

**Где:** [`dist/index.html:60`](../dist/index.html) содержит
```html
<link rel="modulepreload" href="./assets/matrix-CbprGFg3.js">
```
Это не случайность сборки — это следствие статической цепочки импортов:

```
main.ts → App.vue (import { useAuthStore } from "@/entities/auth")
        → entities/auth/model/stores.ts:16 (import ... from "@/entities/matrix")
        → entities/matrix/model/matrix-client.ts:13
          (import * as sdk from "matrix-js-sdk-bastyon/lib/browser-index.js")
```

`App.vue` — корневой компонент, монтируется в `main.ts` до всякой навигации. Значит **весь граф статических импортов до него** (включая полный Matrix SDK) резолвится и **исполняется** ещё до того, как роутер решит, на какой странице находится пользователь. Пользователь, зашедший на `/welcome` или `/login` **без сессии**, всё равно платит:

| Метрика | Значение |
|---|---|
| Размер чанка (raw, минифицированный) | 9.4 МБ |
| Размер чанка (gzip, по сети) | 3.46 МБ |
| Доля от всего JS, скачиваемого до первого кадра | **81%** |

**Почему это плохо именно для Android/слабых сетей:** это не только трафик — это ~9.4 МБ, которые парсер JS-движка должен пройти при старте (top-level код модуля выполняется синхронно в графе зависимостей ES-модулей), на слабом CPU старого Android-устройства это реальные сотни миллишекунд-секунды блокировки главного потока ещё до первого рендера.

**Фикс:** разорвать статическую цепочку. Auth-стору не обязательно тянуть Matrix SDK на уровне модуля — сервис клиента нужен только когда реально восстанавливается сессия / происходит логин:

```ts
// entities/auth/model/stores.ts — вместо статического импорта
// import { getMatrixClientService } from "@/entities/matrix";

// делать это в момент фактического использования:
async function ensureMatrixReady() {
  const { getMatrixClientService } = await import("@/entities/matrix");
  return getMatrixClientService();
}
```

Типы (`import type { UserWithPrivateKeys } from ...`) можно оставить статическими — они не попадают в рантайм-бандл. Это уже частично применяется в `providers/index.ts:147` для Tor-прокси — паттерн в кодовой базе уже есть, нужно распространить его на auth store.

**Ожидаемый эффект:** для `/welcome`, `/login`, `/register`, `/download` — минус ~3.46 МБ gzip и ~9.4 МБ парсинга из критического пути. Для тех, кто уже залогинен и идёт сразу в `/chat`, чанк всё равно догрузится (просто явным `import()` вместо `modulepreload`), но не будет тормозить рендер логин-экрана для остальных.

### 2. Legacy-скрипты грузятся последовательно (waterfall), а не параллельно

**Где:** [`loadChatScripts.ts:69-71`](../src/app/providers/chat-scripts/loadChatScripts.ts#L69-L71)

```ts
// Sequential dependency chain
for (const script of scriptsToLoad.await) {
  await loadScript(normalizeScriptName(script));
}
```

`loadScript()` создаёт `<script>`, ждёт его `onload`, и только **после этого** цикл переходит к следующему файлу — то есть браузер не начинает качать скрипт №2, пока не докачает, не распарсит и не выполнит скрипт №1. Для 13 файлов в цепочке `await` это **13 последовательных сетевых round-trip'ов**.

| Метрика | Значение |
|---|---|
| Файлов в последовательной цепочке | 13 |
| Суммарный payload (gzip) | ~310 КБ |
| Доп. задержка от сериализации при RTT=200мс (типично для мобильной сети / Tor, который проект поддерживает) | **~2.6 с** сверх времени скачивания |

Это стоит дорого именно потому, что приложение явно поддерживает Tor (`useTorStore`, `torService` в `providers/index.ts`) — там RTT легко 300-500мс, и цена сериализации взлетает до 4-6 секунд.

Кроме того, эта цепочка **блокирует монтирование роутера** для всех не-`/download` роутов:
```ts
// providers/index.ts:189-193
if (!isStaticRoute) {
  await withTimeout(scriptsReady, 30_000, "Chat scripts loading");
}
```

**Фикс:** классический браузерный трюк для динамически создаваемых `<script>` — выставить `async = false` явно. По спецификации HTML это заставляет браузер **скачивать все скрипты параллельно**, но **выполнять их в порядке вставки** (то есть зависимость `underscore` → `satolist` → ... сохраняется без единой строчки доп.кода):

```ts
function loadScriptsInOrder(urls: string[]): Promise<void> {
  return new Promise((resolve, reject) => {
    let loaded = 0;
    const scripts = urls.map(src => {
      const el = document.createElement("script");
      el.src = src;
      el.async = false; // fetch parallel, execute in insertion order
      el.onerror = () => reject(new Error(`Failed to load ${src}`));
      return el;
    });
    scripts[scripts.length - 1].onload = () => resolve();
    scripts.forEach(el => document.head.appendChild(el));
  });
}
```

Это даёт тот же гарантированный порядок выполнения (важен для `underscore` → `satolist`/`actions.js`, использующих глобальный `_`), но 13 запросов уходят в сеть одновременно вместо друг за другом.

**Ожидаемый эффект:** экономия сетевой части времени боевого экрана `/chat` — вместо 13×RTT получаем ~1×RTT + время скачивания самого медленного файла. На практике это секунды на мобильной сети, особенно через Tor.

## P1 — существенно, но не блокирует рендер

### 3. Нет visualizer/анализатора бандла в конфиге

Все цифры в этом отчёте получены вручную (`du` + `gzip -c | wc -c` по `dist/`). Это одноразовая археология, а не воспроизводимый процесс. Рекомендуется добавить `rollup-plugin-visualizer`, включаемый по флагу, чтобы next-time не гадать:

```ts
// vite.config.ts
import { visualizer } from "rollup-plugin-visualizer";

plugins: [
  // ...
  process.env.ANALYZE && visualizer({ filename: "dist/stats.html", gzipSize: true }),
].filter(Boolean),
```

### 4. Не-критичные legacy-вендор скрипты всё равно грузятся на старте

`scriptsToLoad.async` (fire-and-forget, не блокирует — это уже хорошо) включает `joypixels.js` (844 КБ raw), `gif-frames.min.js` (384 КБ), `emojionearea*` (~140 КБ), `hammer.min.js` (24 КБ). Они не блокируют рендер, но всё равно скачиваются и парсятся при **каждом** холодном старте, даже если пользователь ни разу не откроет эмодзи-пикер или не запишет GIF за сессию.

**Фикс (опционально, ниже приоритет):** отложить их загрузку до первого реального взаимодействия (открытие панели эмодзи / меню вложений), а не до `setupChatScripts()` на старте приложения.

### 5. Политика кэширования/сжатия не видна из репозитория

Деплой идёт через IIS (`c:\inetpub2025\forta.chat`), но `web.config` в репозитории нет — сжатие (gzip/brotli) и `Cache-Control` для `/assets/*` и `/js/*` целиком зависят от конфигурации сайта на сервере, которая не version-controlled. Vite/сборка тоже не пре-сжимает файлы (`vite-plugin-compression` не подключен).

**Рекомендация:**
- Закоммитить `web.config` с явным `<httpCompression>` (или подтвердить, что IIS Dynamic/Static Compression модули включены на сервере).
- Для хэшированных `dist/assets/*` (имя = хэш содержимого, безопасно кэшировать вечно) — `Cache-Control: public, max-age=31536000, immutable`.
- `dist/js/*` (legacy-скрипты, имена **не хэшируются** — см. `sync-vendor-assets.mjs`) — здесь агрессивный `max-age` опасен (можно застрять на старой версии после бага). Нужен либо cache-busting query (`?v=<build-hash>`), либо короткий `max-age` + `ETag`/`Cache-Control: no-cache` для ревалидации. Сейчас непонятно, что стоит на сервере — стоит проверить отдельно.
- `index.html` уже правильно помечен `no-cache` через `<meta>` — это ок, инвалидация нужна каждый раз, чтобы подхватывать новые хэши ассетов.

## P2 — точечные улучшения, требуют осторожности

### 6. `esbuild.target: "chrome60"` — возможно избыточно консервативно

[`vite.config.ts:76-79`](../vite.config.ts#L76-L79):
```ts
build: {
  // Chrome 60 target matches Android minSdk 24 baseline WebView.
  // Downlevels optional chaining, nullish coalescing, logical assignment
  // so old WebView can parse the bundle without SyntaxError.
  target: "chrome60",
```
Комментарий в том же файле (esbuild.supported.bigint) сам признаёт: *"real Android devices receive WebView updates via Play Store (Chrome 100+)"*. Если это действительно так для основной массы жалующихся пользователей — таргет `chrome60` заставляет esbuild даунлевелить синтаксис (optional chaining, `??`, логические присваивания) во всём графе, включая тяжёлый Matrix SDK с async-генераторами в криптографии/sync — это обычно даёт +10-20% к размеру для SDK-тяжёлого кода за счёт хелперов/полифиллов, которые реально нужны только гипотетическому древнему WebView.

**Не менять вслепую.** В проекте уже есть механизм для проверки: `device_telemetry` в Dexie (`src/shared/lib/telemetry`, собирается после WEE-97). Прежде чем трогать `target`, стоит выгрузить реальные версии WebView/Chrome среди пользователей, у которых баг-репорты — если там действительно превалирует Chrome 100+, поднятие таргета (например до `es2020`/`chrome90`) — самый дешёвый способ ужать самый тяжёлый чанк в бандле без единой строчки логики.

### 7. Нет `preconnect`/`dns-prefetch` для Matrix homeserver / Pocketnet-нод

`index.html` не содержит `<link rel="preconnect">` к дефолтному homeserver или прокси-нодам Pocketnet. Сейчас TLS/DNS handshake к этим origin'ам стартует только когда JS реально делает первый запрос — то есть уже после полной загрузки и инициализации бандла. Добавление `preconnect` для известного дефолтного origin'а — дешёвый и безопасный выигрыш (перекрывает ~100-300мс handshake с временем загрузки скриптов, а не добавляет его после).

## Как воспроизвести цифры из этого отчёта

```bash
npm run build
# Размеры чанков
find dist/assets -iname "*.js" | xargs -I{} du -h {} | sort -rh
# Gzip-размер конкретного чанка
gzip -c dist/assets/<file>.js | wc -c
# Проверить modulepreload в итоговом HTML
grep modulepreload dist/index.html
```
