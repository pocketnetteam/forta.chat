Повод: 4B-модель (текущий единственный вариант) заметно тормозит на слабом Android-телефоне
пользователя — субъективно то же самое семейство жалоб, что и в
`2026-08-20-local-ai-perf-tuning-plan.md` («localai отвечает очень долго»), но **другая причина и
другое решение**: тот план тюнит рантайм-параметры (`n_threads`, `n_batch`, KV-quant, thinking) для
одной фиксированной модели; этот план — про то, чтобы у пользователя вообще была возможность выбрать
**другую, более лёгкую модель** в Настройках, если 4B ему не подходит. Оба плана независимы и не
блокируют друг друга: перф-тюнинг применяется к любой выбранной модели, выбор модели не отменяет
пользу от тюнинга.

Оба репозитория одновременно:

- `C:\inetpub2025\forta.chat` — потребитель: стор + UI выбора модели в Настройках.

## 1. Текущее состояние (прочитано из кода, не предположение)

Манифест — **не список**, а ровно один `model: ModelArtifact` + один `embedding: EmbeddingArtifact`
(`manifest.schema.ts:9-16`). `previousModels`/`previousEmbeddings` — история версий для отката
(«эта модель раньше была v1, стала v2»), **не** альтернативы на выбор пользователя.

Это осознанное архитектурное решение, но не про «одна модель навсегда» — TZ §5.1 («Почему не
«пара»») явно формулирует его как «модель и эмбеддинг — два независимых top-level поля со своей
версией/историей», а совместимость эмбеддинга с моделью(-ями) уже декларируется явным полем
`EmbeddingArtifact.compatibleModelIds: string[]` — **массив уже сегодня**, специально рассчитанный
на то, что один эмбеддинг может обслуживать несколько разных моделей. Это создаёт готовую опору: не
нужно делать эмбеддинг per-model выбираемым руками — можно резолвить его автоматически по
`compatibleModelIds` выбранной модели (см. §4).

Остальная инфраструктура уже частично рассчитана на множественность:
- `ModelRegistry` (`model-registry.ts:34`) хранит строки `installed_artifacts`, ключованные по
  `(kind, artifact_id, version)`, с отдельным флагом `is_current` — то есть уже умеет держать
  историю разных id, просто `getCurrent()`/`setCurrent()` всегда резолвят «текущий» как один на
  `kind`. Переключение на другой `artifact_id` для того же `kind` — штатный вызов
  `setCurrent('model', { id: otherModelId, ... })`, ничего в схеме таблицы менять не нужно.
- Пороги eligibility (`minRamGb`/`recommendedRamGb`) — **уже per-artifact поля**, не константы кода
  (`manifest.schema.ts:34-36`, `eligibility-service.ts:16-31`) — `evaluateEligibility()` принимает
  произвольный `artifact`, для другой модели просто вызывается с другими числами.
- `LlamaCppCapacitorAdapter.loadModel()` грузит `.gguf` по произвольному пути — движок не завязан на
  конкретный файл, ограничений на смену модели на уровне рантайма нет.

Чего нет:
- `LocalAiClient.switchModel()` (`local-ai-client.ts:704`) всегда таргетит
  `this.currentManifest.model` — нет понятия «переключиться на конкретный `modelId` из нескольких».
  Он же удаляет старый файл модели при переключении (шаг 6, `:730-733`) — то есть «одна модель на
  диске одновременно» уже дефолтное поведение, просто привязанное к «манифест обновился», а не
  «пользователь выбрал другую модель».
- `ManifestDiff` (`manifest.diff.ts:11-16`) — тоже singular (`model: { from?, to }`).
- `forta.chat`: `LocalAiSettingsSection.vue` рисует ровно одну карточку модели
  (`model.displayName`/`.quant`/`.sizeBytes`, строки 196-219) — списка моделей нет физически.
  `local-ai-store.ts`'s `currentModel` — `ref<ModelArtifact | null>`, тоже singular
  (`local-ai-store.ts:76`). `MODEL_DOWNLOADED_MARKER_KEY` (`:19`) — один булев маркер на устройство
  («модель когда-то была скачана»), не привязан к конкретному `modelId`.
- Реальный манифест на `https://bastyon.com/local-ai-manifest.json`
  (`MANIFEST_URL_PLACEHOLDER`, `create-client.ts:11`) содержит одну модель — вторую туда никто не
  публиковал.

## 2. Общие принципы

- **Аддитивно там, где возможно.** Новый API (`selectModel()`, второй параметр у
  `checkDeviceEligibility()`) — не ломает существующие вызовы с одной моделью в манифесте: если
  `models.length === 1`, поведение не отличается от сегодняшнего (авто-выбор единственной модели).
- **Одна модель на диске одновременно** (см. §4) — явное продуктовое решение, а не техническое
  ограничение: аудитория проекта — слабые/старые Android-устройства с ограниченным хранилищем
  (`CLAUDE.md`'s «Устройства: Android 7.0+»), 2-4 ГБ на лишнюю модель «про запас» — плохой размен на
  этом сегменте. Технически ничего не мешает разрешить несколько installed одновременно
  (`ModelRegistry` это переживёт), просто явно не делаем на первой итерации.
- **Порядок пересборки/проверки** — тот же, что в перф-плане (`device-ai-loop.md`): правки в
  `local-ai/src/**` → `npm run lint && npm run typecheck && npm run test:unit && npm run test:integration && npm run build`
  → `forta.chat`'s `npm run cap:run` (подхватывает `dist/` через symlink) → реальный прогон на
  устройстве.
- **Тесты обязательны на каждую фазу** (оба `CLAUDE.md`).
- **Отдельная ветка** — не коммитить поверх `llama2-perf` (перф-план другая задача); завести
  `llama2-model-select` (или аналог) от актуального `master`/`llama2`.
- **Не пересекаться с параллельной задачей по клавиатуре** — весь объём здесь: схема манифеста,
  клиентский API, стор, Настройки. Ни один файл ввода/composer/клавиатуры не трогается.

## 3. Фаза 1 — схема манифеста: `model`/`embedding` → массивы

### Дизайн
`manifest.schema.ts`:
```ts
export interface LocalAiManifest {
  manifestVersion: number;
  publishedAt: string;
  models: ModelArtifact[];
  embeddings: EmbeddingArtifact[];
  previousModels?: ModelArtifact[];
  previousEmbeddings?: EmbeddingArtifact[];
}
```
`ModelArtifact`/`EmbeddingArtifact` сами не меняются — `compatibleModelIds` на `EmbeddingArtifact`
уже массив (§1), достаточно для резолва «какой эмбеддинг подходит выбранной модели».

Открытый вопрос по порядку элементов в `models[]`: манифест — источник правды и про «какая модель
рекомендуется по умолчанию» для нового пользователя. Не гадать порядком массива — добавить явное
`recommended: boolean` на `ModelArtifact` (ровно одна модель с `true` на манифест, публикующая
сторона решает, а не код). Без этого поля клиенту/UI пришлось бы либо брать `models[0]` (хрупко,
неявно), либо самому решать «рекомендуемая = самая маленькая, что проходит eligibility» — тоже
валидный вариант, но это политика продукта, не техническая деталь; см. §9 п.1, финальное решение —
за пользователем перед реализацией.

### Тесты
- `local-ai/test/unit/manifest` (найти существующие тесты `manifest.schema.ts`, если типы там
  проверяются рантайм-гардами) — на этом шаге в основном компиляционная проверка (TypeScript), живая
  логика проверяется в Фазе 2.

## 4. Фаза 2 — `validateManifest()` для массивов

### Дизайн
`manifest.service.ts`:
- `model`/`embedding` разбор (строки 49-96) — заменить на цикл по `m.models`/`m.embeddings`, каждый
  элемент валидируется теми же правилами, что сейчас (id/version/paramsB/filename/sha256/sizeBytes/
  minRamGb/recommendedRamGb/pinned revision). Ошибка формулируется с индексом
  (`models[1].sha256 is not a valid hex64 string`) — при нескольких моделях «model.sha256 is not
  valid» без индекса не даёт понять, какая из них сломана.
- `models` не может быть пустым массивом (хотя бы одна модель — иначе `ensureModelReady()` нечего
  делать).
- Перекрёстная проверка `compatibleModelIds` — уже есть для одиночной пары (`:93-95`), расширяется:
  для каждой активной (`status: 'active'`) модели должен существовать хотя бы один `embeddings[]`-
  элемент с этим id в `compatibleModelIds`. Отсутствие подходящего эмбеддинга для активной модели —
  ошибка валидации, не молчаливый пропуск (иначе `ensureEmbeddingReady()` для этой модели упадёт
  только в рантайме, на устройстве, а не на этапе публикации манифеста).
- `maxModelParamsB` (конструктор `ManifestService`, `:125`) — уже общий потолок, применяется к
  каждой модели массива тем же способом, что сейчас к одной. Не менять смысл: манифест может
  содержать модель крупнее потолка (например, будущий более мощный вариант) — такая модель просто
  **не проходит валидацию целиком** сегодня (`ManifestValidationError`, весь манифест отклоняется).
  Это неверно для мультимодельного манифеста: 4B-модель, не проходящая `maxModelParamsB`, не должна
  ронять валидность 1.5B-модели рядом с ней в том же манифесте. См. §9 п.2 — нужно решить, меняется
  ли семантика `maxModelParamsB` с «весь манифест невалиден» на «эта конкретная модель исключается
  из `models[]`, остальные проходят», прежде чем реализовывать.

### Тесты
- Расширить существующие юнит-тесты `validateManifest()` (искать `manifest.service.test.ts` или
  аналог в `test/unit`) — массив из 2 моделей с одним битым полем даёт ошибку с индексом; пустой
  `models: []` — ошибка; активная модель без совместимого эмбеддинга — ошибка; модель со
  `status: 'deprecated'` без совместимого эмбеддинга — НЕ ошибка (deprecated не обязана быть
  скачиваемой).

## 5. Фаза 3 — `diffManifest()` по массивам

### Дизайн
`manifest.diff.ts` — `ManifestDiff.model`/`.embedding` (singular `{from?, to}`) не масштабируется на
список произвольной длины. Заменить на `models: Array<{ id: string; from?: ModelArtifact; to?:
ModelArtifact; changed: boolean }>` (аналогично `embeddings`) — по одному элементу на объединение
id из `next`/`installed`, `to` отсутствует, если модель пропала из нового манифеста (deprecated →
снята), `from` отсутствует, если модель появилась впервые. `modelChanged`/`embeddingChanged` (булевы
флаги верхнего уровня) — оставить как «изменилось ли **что-то** в списке» (`.some(m => m.changed)`)
для обратной совместимости мест, которые слушают только факт изменения, не детали.

`installed` для сравнения (см. doc-комментарий `:18-26`) по-прежнему best-effort до
`ModelRegistry`'s чтения — здесь ничего не меняется концептуально, только форма данных.

### Тесты
- `manifest.diff.test.ts` (если существует, иначе завести) — 2 модели в `next`, 1 в `installed`
  (совпадает по id/version) → один `changed: false`, один `changed: true` (`from: undefined`); модель
  пропала из `next` → `to: undefined`, `changed: true`.

## 6. Фаза 4 — явный выбор модели в `LocalAiClient`

### Дизайн
Ядро всей задачи. Сейчас `ensureModelReady()`/`switchModel()` читают `this.currentManifest!.model`
напрямую (`:707`, и аналогично в `ensureModelReady()` — найти точную строку при реализации, тот же
паттерн). Нужно:

1. Новое персистентное состояние — `selectedModelId` в `kv_store` (тот же паттерн, что
   `manifest:cached`/`manifest:etag` в `ManifestService`, но это состояние `LocalAiClient`-уровня, не
   `ManifestService`-уровня — выбор модели переживает обновление манифеста, а не привязан к нему).
   Дефолт при первом запуске (ничего не выбрано): модель с `recommended: true` из §3, либо (если это
   поле решили не заводить) первая `status: 'active'` модель — см. §9 п.1.
2. Новый публичный метод:
   ```ts
   async selectModel(modelId: string): Promise<void>
   ```
   Валидирует, что `modelId` есть среди `manifest.models` и `status === 'active'`, пишет в
   `kv_store`, эмитит новое событие `model:selected` (аналог `manifest:updated`) — **не скачивает и
   не грузит** ничего сама, чисто меняет намерение (симметрично тому, как `refreshManifest()` не
   стартует скачивание автоматически, TZ §5.4 «Скачивание не стартует автоматически по факту
   diff»). Реальная загрузка — отдельный явный вызов `ensureModelReady()`/`switchModel()` после
   выбора, как сегодня для «Скачать».
3. `ensureModelReady()`/`switchModel()` резолвят целевой артефакт как
   `manifest.models.find(m => m.id === (await this.getSelectedModelId()))` вместо
   `this.currentManifest!.model`. Если выбранная модель пропала из манифеста (deprecated/удалена
   публикующей стороной) — fallback на дефолт из шага 1, не молчаливый краш.
4. `switchModel()`'s шаг 6 (удаление старого файла, `:730-733`) — логика не меняется, просто источник
   «какой файл новый/старый» теперь `selectedModelId`, а не версия одной фиксированной модели.
   Побочный эффект уже правильный: смена модели пользователем = `switchModel()`-подобный поток
   (release context → download+verify новую → **удалить старую** → invalidate session cache → load).
   Стоит рассмотреть, нужен ли отдельный публичный метод (`switchToModel(modelId)`) вместо
   перегрузки `switchModel()` без параметров — вероятно да, для ясности API: `switchModel()` без
   аргументов остаётся «обновить текущую до новой версии из манифеста» (roadmap-совместимость),
   `selectModel(id)` + следующий `ensureModelReady()`/явный `switchModel()` — «пользователь выбрал
   другую модель». Решить точную сигнатуру при реализации, не задача этого документа.
5. `EmbeddingArtifact`-резолв для выбранной модели — `manifest.embeddings.find(e =>
   e.compatibleModelIds.includes(selectedModelId))`. Если моделей с разными required-dimensions
   несколько и у каждой свой эмбеддинг — `ensureEmbeddingReady()` должен переключаться вместе со
   сменой модели (тот же `switchEmbedding()`-поток, `:762`), не оставлять эмбеддинг от предыдущей
   модели висеть несовместимым. `VectorStore`'s space guard (TZ §8.2/§8.3, уже упомянут в doc-
   комментарии `switchEmbedding()`) — существующая защита от использования векторов с чужой
   размерностью, ничего нового изобретать не нужно, просто убедиться, что смена модели триггерит тот
   же путь.

### Тесты
- Интеграционные на `local-ai-client.ts` (расширить существующий файл, тот же, что использовался для
  Фаз 3-5 перф-плана) — `selectModel()` без последующего `ensureModelReady()` не качает; выбор
  несуществующего/deprecated id — throw; `ensureModelReady()` после `selectModel('small-model')`
  грузит `small-model`'s файл, не дефолтную; смена выбора после того, как одна модель уже установлена
  → `switchModel()`/аналог удаляет старый файл, session cache инвалидируется (тот же ассерт, что уже
  есть для обычного `switchModel()`); дефолт при отсутствии явного выбора — берёт `recommended`/первую
  активную модель.

## 7. Фаза 5 — eligibility per-model

### Дизайн
`evaluateEligibility()`/`EligibilityService.evaluate()` уже принимают произвольный artifact
(`minRamGb`/`recommendedRamGb`/`sizeBytes`) — никакой новой логики принятия решения не нужно
(§1). Нужно только:
- `LocalAiClient.checkDeviceEligibility(target, modelId?)` — второй опциональный параметр, чтобы
  проверить eligibility **конкретной** модели из списка, не только текущей выбранной — иначе UI
  списка моделей (§9) не сможет показать бейдж «не влезет» рядом с моделью, которую пользователь ещё
  не выбрал. Без модели — дефолт на `selectedModelId` (обратная совместимость с сегодняшним
  однопараметровым вызовом).
- Ничего не меняется в самом `EligibilityService`/`evaluateEligibility()` — они уже per-artifact.

### Тесты
- `local-ai-client.test.ts` — `checkDeviceEligibility('model', 'small-model-id')` на устройстве с
  малым RAM даёт `'ok'`, `checkDeviceEligibility('model', '4b-model-id')` на том же снапшоте даёт
  `'no'`/`'tight'` — оба вызова не мутируют `selectedModelId`, чисто readonly проверка.

## 8. Фаза 6 — `forta.chat`: стор

### Дизайн
`local-ai-store.ts`:
- `currentModel: ref<ModelArtifact | null>` (singular, `:76`) → добавить рядом
  `availableModels: ref<ModelArtifact[]>` (из `manifest.models`, только `status: 'active'`) и
  `selectedModelId: ref<string | null>`. `currentModel` можно оставить как computed
  (`availableModels.find(m => m.id === selectedModelId)`) для минимального диффа в местах, которые
  его уже читают (`AiModelGate.vue` и т.п.) — не задача менять их в этой фазе, если они не
  завязаны на выбор конкретно.
- Новая функция `modelEligibility(modelId: string): EligibilityReport | null` — обёртка над
  `client.checkDeviceEligibility('model', modelId)` из Фазы 5, с локальным кэшем per-modelId (не
  гонять сетевой/device-info запрос на каждый рендер списка).
- `selectModel(address, modelId)` — вызывает `client.selectModel(modelId)` (Фаза 4), обновляет
  `selectedModelId`. Персистентность выбора — тот же паттерн, что `MODEL_DOWNLOADED_MARKER_KEY`
  (`:19-46`), но per-account (`local_ai_selected_model_${address}`), не device-wide: два аккаунта на
  одном устройстве — потенциально разный выбор модели (roadmap 2.1's per-account изоляция уже
  прецедент, `databaseName` в `create-client.ts:81` тот же принцип).
- `MODEL_DOWNLOADED_MARKER_KEY` (`:19`) — сейчас один булев маркер «модель когда-то была скачана»,
  без привязки к id. С несколькими моделями это должно стать «какая именно модель скачана» —
  переименовать/расширить в `local_ai_downloaded_model_id` (хранит id, не булево), и
  `restoreModelIfPreviouslyDownloaded()` (`:386-390`) должен восстанавливать **ту же** модель, что
  была скачана в прошлой сессии, а не безусловно текущую выбранную (которая могла смениться, если
  пользователь передумал между сессиями, но это состояние ещё не синхронизировано — редкий край-кейс,
  решить при реализации: скорее всего маркер должен обновляться в `selectModel()`/`downloadModel()`
  парой, не рассинхронизироваться).
- `switchModel(address)` (`:398-415`) — сегодня без параметра; либо остаётся «обновить текущую до
  новой версии» и добавляется параллельный `switchToModel(address, modelId)`, либо получает
  опциональный `modelId` параметр — синхронизировать с итоговой сигнатурой `LocalAiClient` из Фазы 4.

### Тесты
- `local-ai-store.test.ts` — `selectModel()` меняет `selectedModelId` и персистит его per-account;
  `availableModels` фильтрует `deprecated`; `modelEligibility()` кэширует по modelId, не дергает
  device-info повторно для того же id; смена аккаунта (`ensureClient` с другим `address`) не тащит
  выбор модели предыдущего аккаунта.

## 9. Фаза 7 — `forta.chat`: UI пикер в Настройках

### Дизайн
`LocalAiSettingsSection.vue` — заменить единственную карточку модели (строки 196-219) на список:
для каждой `availableModels` — строка с `displayName`/`quant`/`paramsB`/`sizeBytes`, eligibility-
бейдж (тот же паттерн, что уже есть, `:100-107`, но на каждую строку своего вычисления через
`modelEligibility(model.id)` из Фазы 6), и action-кнопка, зависящая от состояния этой конкретной
модели:
- ещё не скачана → «Скачать» (как сегодня, `handleDownload`, но с `modelId`).
- скачана и выбрана (`selectedModelId === model.id` && `modelReady`) → «Активна» / кнопка удаления,
  как сегодня.
- скачана другая модель, эта — нет → «Скачать и переключиться» (по сути `selectModel(id)` →
  `downloadModel`/`switchModel(id)` одним действием пользователя, не два отдельных тапа).
- недоступна по eligibility (`verdict === 'no'`) → диз­эйблена, бейдж вместо кнопки — тот же паттерн,
  что уже есть для `disabled="eligibility?.verdict === 'no'"` на кнопке скачивания (`:253`).

Раздел «Update»/«Check for updates» (`handleUpdate`/`handleCheckUpdates`, `:139-159`) логически не
меняется — «проверить обновления манифеста» остаётся общим действием не зависящим от того, сколько
моделей в списке; «Обновить» относится к уже выбранной модели конкретно (обновить её версию, не
сменить модель — два разных действия, не путать в UI одной кнопкой).

### Тесты
- `LocalAiSettingsSection.test.ts` (расширить существующий) — рендерит N строк для N моделей из
  `availableModels`; клик по недоступной по RAM модели не вызывает `downloadModel`; клик по «скачать
  другую» вызывает `selectModel` перед `downloadModel`/`switchModel`.

## 10. Фаза 8 — публикация второй модели (не код, внешняя зависимость)

Без этого шага вся работа выше невидима пользователю — реальный манифест на
`https://bastyon.com/local-ai-manifest.json` (`MANIFEST_URL_PLACEHOLDER`) сегодня содержит одну
модель. Нужно:
- Выбрать конкретную меньшую модель (напр. 1.5B-2B того же семейства/квантования, что и текущая 4B,
  для консистентности качества ответов) и совместимый эмбеддинг (тот же, если совпадает
  `compatibleModelIds`-размерность, либо отдельный).
- Посчитать `sha256`/`sizeBytes`, запинить `revision` (HuggingFace commit SHA, не `main`/`HEAD` —
  та же валидация, `manifest.service.ts:67-70`), разметить `minRamGb`/`recommendedRamGb` для
  реально более слабых устройств.
- Согласовать с тем, кто управляет манифестом (product owner, см. `create-client.ts:9`'s комментарий
  «not necessarily the final production URL — confirm with the product owner»).

Разработку/тесты Фаз 1-7 это не блокирует — юнит/интеграционные тесты `local-ai` используют
фейковый манифест (`FakeLlmRuntimeAdapter`/тестовые фикстуры), а device-loop-верификацию
(`device-ai-loop.md`) можно прогнать на временном тестовом манифесте с двумя маленькими моделями
(не обязательно финальными) — только для проверки, что переключение вообще работает end-to-end на
реальном устройстве.

## 12. Открытые вопросы (решить до/во время реализации, не блокируют старт Фазы 1-3)

1. Поле `recommended: boolean` на `ModelArtifact` (§3) vs вычисление «рекомендуемой» модели на
   стороне клиента (например, «самая мощная, что проходит `'ok'` eligibility на этом устройстве») —
   первое проще и предсказуемее, второе не требует лишнего поля в манифесте и более персонализировано
   под конкретное устройство. Рекомендация: явное поле в манифесте (проще, отлаживаемо, не зависит от
   правильности client-side эвристики) — но решение продуктовое, не техническое.
2. Семантика `maxModelParamsB` при нескольких моделях в манифесте (§4) — «вся модель исключается из
   списка, если больше потолка» (совместимо с целью параметра — не пускать слишком тяжёлые модели на
   этот класс устройств) vs «весь манифест невалиден, если хоть одна модель больше потолка»
   (сегодняшнее поведение, сломает публикацию любого манифеста, где есть и лёгкая, и тяжёлая модель).
   Первое нужно почти наверняка для этой задачи — решить явно перед Фазой 2, не по умолчанию.
3. Точная сигнатура «переключиться на другую модель» в `LocalAiClient` (§6 п.4) —
   `switchModel(modelId?)` (один метод, опциональный параметр) vs `selectModel(id)` +
   `switchModel()` как два отдельных вызова (симметрично `refreshManifest()`+`switchModel()`
   сегодня). Второе яснее по контракту («выбор — не сеть», «переключение — сеть+диск»), но добавляет
   пользователю (`forta.chat`) на один await больше. Решить при реализации Фазы 4 совместно с ревью.
4. Разные `contextLength`/`chatTemplate` у разных моделей — `SessionCache`'s `modelFingerprint`
   (упомянут в перф-плане §1, `local-ai-client.ts:847`/`:896`) уже различает модели по некоторому
   отпечатку для инвалидации KV-кэша; убедиться, что этот fingerprint включает `modelId`, не только
   версию — иначе смена модели A→B той же версии(??) теоретически могла бы попытаться переиспользовать
   чужой session-кэш. Скорее уже корректно (fingerprint почти наверняка включает id), но стоит
   явно проверить тестом в Фазе 4, не полагаться на «наверное».
5. UI: сколько моделей реально в манифесте на первой итерации — 2 (текущая 4B + одна лёгкая) или
   больше. Список из 2 элементов не требует ничего специального (скролл/поиск); больше 3-4 —
   возможно, потребует более компактной вёрстки, чем «строка на модель» из §9. Не блокирует
   реализацию (§8's меньшая модель — первая и пока единственная новая), но стоит держать в уме при
   вёрстке §9, чтобы не переделывать при добавлении третьей модели позже.
6. iOS — вне объёма (проект Android-first, `CLAUDE.md`), но `selectedModelId`/`downloaded model id`
   персистентность в `kv_store` платформо-независима на уровне `local-ai`, так что здесь ничего
   Android-специфичного не закладывается случайно.
