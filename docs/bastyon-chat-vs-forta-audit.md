## 1. Общая картина

| | bastyon-chat (2020, старый) | forta.chat (2025, новый) |
|---|---|---|
| Фреймворк | Vue 2 + Vuex | Vue 3 + Pinia + TypeScript strict |
| Источник истины | `matrix-js-sdk-bastyon` `IndexedDBStore` (SDK-нативный) + Vuex как производное состояние | Dexie (IndexedDB) как **явный** local-first источник истины, SDK — только транспорт |
| Обновление UI-таймлайна открытого чата | **Поллинг раз в 300 мс** (`setInterval`) поверх `TimelineWindow`, пересборка из состояния SDK | Событийная запись через `EventWriter` в Dexie + `useLiveQuery` (реактивные подписки на IndexedDB) |
| Отправка сообщений | Прямой вызов SDK `sendMessage`/`sendEvent`, retry — только вручную по кнопке «Resend» | `SyncEngine` — pending-очередь в Dexie, FIFO по комнате, exponential backoff + jitter, автоматические ретраи |
| E2E-шифрование | Кастомная схема на secp256k1-ключах Bastyon (не Olm/Megolm), `pcrypto.js` | Тот же кастомный протокол, почти дословно перенесённый в `matrix-crypto.ts` (`Pcrypto`/`PcryptoRoom`) |
| Реконнект/офлайн | Полностью делегирован SDK, плюс мёртвый (не подключённый) код на случай ручного форс-ресинка | Три независимых слоя ретраев (client-level retry, mirror-failover watchdog, SyncEngine watchdog) |
| Кэш расшифрованных сообщений | `ChatStorage` (IndexedDB + полное зеркало в памяти), TTL 30 дней, самоочистка | Расшифровка кешируется в самих Dexie-записях сообщений, отдельный `DecryptionWorker` с двухуровневым backoff |
| Тестовое покрытие протокольного слоя | Отсутствует (нет тестов вообще в проекте) | Очень плотное — десятки unit/regression-тестов на `sync-engine`, `event-writer`, `chat-store` и т.д. |
| Размер «god-файла» с бизнес-логикой чата | `store.js` — 1003 строки | `chat-store.ts` — **7567 строк**, 44 co-located тестовых файла |

**Главный вывод:** forta.chat — это не «сломанный с нуля» протокольный слой. Наоборот, во многих
местах (SyncEngine, DecryptionWorker, EventWriter, connect-matrix-with-retry) реализация **заметно
более продумана и лучше документирована**, чем в bastyon-chat, с явными комментариями вида
`WEE-NN`/`forta-bugs#NNN`, описывающими конкретный продакшен-инцидент, из-за которого появился тот
или иной защитный механизм. Проблема не в отсутствии инженерной культуры, а в:

1. **одном перегруженном God Store** (`chat-store.ts`), который дублирует часть логики `EventWriter`
   и держит реактивное состояние всех комнат в одном `shallowRef`;
2. **нескольких конкретных, точечных багах** (утечка таймера, неограниченный `triggerRef` на весь
   объект сообщений), которые сильно правдоподобно объясняют «лаги анимаций / зависающие кнопки»;
3. **отсутствии одного-двух конкретных «hard-won» защитных паттернов** из bastyon-chat, которые в
   forta.chat пока не перенесены (например, throttling уведомлений/звука, self-healing при поломке
   локальной БД).

Ниже — детальный разбор по слоям протокола, а затем — приоритизированный список конкретных
исправлений.

## 2. Жизненный цикл Matrix-клиента

### bastyon-chat (`src/application/mtrx.js`)

- Ручной кэш креденшлов в `localStorage` независимо от SDK (`lsdatakey + username`), валиден 31 день;
  логин всегда выполняется заново, но если возвращённый токен «вечный» (нет `expires_in_ms`), в ход
  идёт кэш, если он свежее суток — вероятно, чтобы держать серверную сессию живой, не плодя новые
  device-id при каждом заходе.
- **Самолечение через снос кэша токена**: если `IndexedDBStore.startup()` или `startClient()`
  падают — кэшированный токен в `localStorage` **удаляется**, и следующий запуск идёт с чистого
  листа (новый логин/регистрация). Это единственный ответ старого приложения на «повреждённая
  локальная БД» — не «почини на месте», а «сбрось credentials, войди заново».
- `pingServers()` — гонка между основным доменом и зеркалами (Bastyon — Tor/mirror-heavy платформа),
  победитель становится `baseUrl`.
- 7 поколений ключей deviceId в localStorage (`m_device` … `m8_device`) — прямое свидетельство многих
  лет живых миграций именно в этом месте кода.

### forta.chat (`src/entities/matrix/model/matrix-client.ts`)

- `MatrixClientService` — синглтон с явным `SyncWatchdog` (`sync-failover.ts`): считает подряд идущие
  `ERROR`-состояния синка, при превышении порога запускает `recreateOnNextMirror()`, который **сначала
  пробует достучаться до нового хоста и только потом уничтожает старый клиент** — специально, чтобы не
  оставить приложение с `client = null` из-за кратковременного DNS-сбоя.
- Есть защита от двойной регистрации `CallEventHandler`/`GroupCallEventHandler` (эта пара, если её не
  создать вручную и не подавить ленивый стартер SDK, по комментарию в коде «клобберит» свежий звонок —
  прямая связь с жалобами на пропадающий звук в звонках).
- `destroy()` аккуратно останавливает watchdog, оба backoff-таймера, снимает все листенеры.

**Вывод:** сам класс жизненного цикла клиента в forta.chat написан не хуже, местами лучше bastyon-chat
(явные защиты от гонок при пересоздании). Но у forta.chat **нет аналога self-healing «снеси кэш токена
и войди заново»** на случай повреждения именно `IndexedDBStore`/Dexie — см. рекомендацию R5 в разделе 6.

## 3. Синхронизация и обработка таймлайна

### bastyon-chat: гибридная модель — «poll + push для реакций»

Это самое неожиданное архитектурное отличие. Открытый чат в bastyon-chat **не обновляется по мере
прихода событий** — вместо этого `components/chat/list/index.js` держит `setInterval(this.update, 300)`,
который каждые 300 мс пересобирает видимый список сообщений из `TimelineWindow` SDK
(`autoPaginateAll()` → `getEventsAndEncrypt()`). Единственное исключение — реакции: на каждый
смонтированный `MatrixEvent` вешается прямой листенер `Event.relations`/`MatrixEvent.relations`,
симметрично снимаемый в `beforeDestroy()`.

Список чатов (`FETCH_CHATS`/`FETCH_EVENTS` в `store.js`) обновляется **полностью пересчитываясь** на
каждый тик `sync` — без инкрементальных редьюсеров, но с explicit дедуп-guard'ом
(`SET_EVENTS_TO_STORE`, `store.js:432-474`): если id первого события в новом срезе таймлайна совпадает
с уже сохранённым — `Vue.set` вообще не вызывается, чтобы не плодить лишний реактивный шум на каждый
sync-тик, когда по факту ничего не изменилось для этой комнаты.

Дедупликация построена на `clearEventId()` (резолвинг edit-relation к id оригинального события) +
сортировка по `origin_server_ts` в JS (`_.sortBy`) — ordering не доверяется «сырому» порядку из SDK.

### forta.chat: событийная запись через `EventWriter`

`EventWriter` (`shared/lib/local-db/event-writer.ts`) — единственная точка записи входящих событий в
Dexie. Два пути:

- **Небуферизованный** (`writeMessage`) — одна Dexie-транзакция на событие, дедуп по `clientId` (своё
  эхо), затем по `eventId` (дубликат синка).
- **Буферизованный** (`enableBatching()`/`flushBatch`) — `WriteBuffer` коалесцирует пачки по 150 мс/50
  событий в одну транзакцию, специально под sync catch-up burst (комментарий `WEE-93`).

Edits/poll-votes/poll-ends, которые прилетают раньше своей цели, складываются в `pendingEdits`/
`pendingPollVotes` (TTL 5 минут, LRU-кап 200 записей) и «доигрываются», когда цель наконец появляется —
это концептуально более надёжный ответ на «сообщение и его правка/голос пришли не по порядку», чем
подход bastyon-chat (там edits просто резолвятся лениво через relations-индекс SDK при каждом чтении).

**Слабое место (не проверялось построчно, но логика явно недокументирована тестами):**
`flushBatch` оборачивает запись каждого элемента пачки в try/catch (`event-writer.ts:271`) — одно
повреждённое событие не рушит всю транзакцию, что хорошо, но **тихо** — только `console.error`, без
какого-либо retry/dead-letter и без сигнала пользователю, что конкретное сообщение из диалога
безвозвратно потеряно локально. У `DecryptionWorker` для похожего случая («не смогли расшифровать»)
есть структурированный терминальный статус `decryptionStatus: "failed"`, а у `EventWriter` для «не
смогли распарсить» — нет ничего подобного.

**Вывод по разделу:** сам механизм записи в forta.chat концептуально сильнее (транзакционность,
buffered writer, отложенная доигровка edits/голосов). Проблема не в надёжности записи, а в том, что
**чтение** этих данных обратно в реактивный UI-стейт устроено хуже, чем в bastyon-chat — см. раздел 4.

## 4. Реактивность и «лаги анимаций» — ключевая находка

Это раздел, который прямее всего объясняет жалобы «прыгающий UI», «лагают анимации», «зависают
кнопки», перечисленные в описании проекта.

### bastyon-chat: осознанное разделение «горячих» и «холодных» веток state

Typing/read receipts/presence **никогда** не попадают в дедуплицированный `events`-стейт — у них
отдельные, изолированные ветки Vuex (`state.typing`, `state.readreciepts`), специально чтобы
эфемерные, часто тикающие данные не вызывали перерендер (сравнительно дорогого, `Vue.set`-diff'ящего)
списка сообщений. Плюс — упомянутый выше explicit дедуп-guard в `SET_EVENTS_TO_STORE`, не дающий
Vuex-мутации сработать, если по факту ничего не изменилось.

### forta.chat: единый `shallowRef` на **все** комнаты + `triggerRef` без батчинга

`chat-store.ts` хранит сообщения всех комнат в одном `shallowRef<Record<string, Message[]>>` — и
практически каждая функция, меняющая хотя бы одно сообщение в хотя бы одной комнате, заканчивается
вызовом `triggerRef(messages)` (это не единичный случай — grep находит **20+ мест** в файле, где
`triggerRef(messages)` вызывается на весь общий ref: `chat-store.ts:4046, 4143, 4671, 4721, 4740, 4763,
4793, 4824, 4845, 4872, 5716, 6103, 6128, 6161, 6203, 6437, 6465, 6926, 6970, 7046, 7098, 7288` и др.).

`triggerRef` форсирует Vue считать **весь** ref изменившимся — то есть каждый watcher/computed,
читающий `messages.value` где угодно в приложении (в первую очередь `activeMessages`, питающий
`ChatVirtualScroller`), пересчитывается **на каждое** входящее событие в **любой**, даже неактивной,
комнате.

Конкретно `addMessage()` (`chat-store.ts:4653-4671`):

```ts
// с комментарием в самом коде:
// With shallowRef + no-spread in activeMessages, in-place push wouldn't
// change the reference and watchers wouldn't fire.
messages.value[roomId] = [...messages.value[roomId], message];
triggerRef(messages);
```

вызывается **безусловно на каждое входящее timeline-событие в каждой комнате**, включая фоновые.

**Сценарий отказа:** пользователь возвращается в сеть после разрыва на нестабильном Android-соединении
(ровно то, что описано в проекте как типичный кейс) — за несколько секунд догоняющий синк приносит
десятки-сотни событий по многим комнатам. Каждое из них дергает полный array-copy + полную инвалидацию
общего ref, без дебаунса, **на главном потоке**, прямо в момент, когда пользователь пытается
скроллить/тапать по кнопке. Это структурно то же самое, от чего в forta.chat уже есть **два готовых
инструмента**:

- `shared/lib/patch-scheduler.ts` — rAF-батчинг нескольких реактивных писателей в один рендер
  (специально против flicker под `contain: strict`);
- `shared/lib/burst-coalescer.ts` — settle/max-wait дебаунс, чтобы «капающий» бэклог не пересортировывал
  сайдбар на каждое сообщение (комментарий в файле прямо называет цель: «every message reorders the
  chat list»).

Оба инструмента подключены к пути обновления **сайдбара** (список чатов), но **не** к пути обновления
`messages`/`addMessage()` — то есть команда уже один раз решала ровно эту проблему для одного места и
не распространила решение на другое, где она бьёт сильнее (открытый диалог, куда пользователь
непосредственно смотрит и с которым взаимодействует).

**Рекомендация (см. R1 в разделе 6):** завести per-room `shallowRef` (или `Map` ref с точечным
`triggerRef` только для затронутой комнаты) вместо одного глобального `shallowRef` на все комнаты, и/или
прогнать поток входящих фоновых событий через `patch-scheduler`/`burst-coalescer`, как уже сделано для
сайдбара.

## 5. Отправка сообщений и очередь

### bastyon-chat

Локальное эхо, txn-id reconciliation и retry-при-rate-limit **полностью делегированы** встроенному
scheduler'у matrix-js-sdk — собственной очереди/бэкоффа в приложении нет вообще. Единственное, что
добавляет сам код:

- к каждому отправляемому сообщению приклеивается замыкание `resendMessage = () =>
  this.sendXxx(...arguments)` — повтор отправки инициируется **только вручную**, кнопкой «Resend» в
  UI, старое неудавшееся локальное эхо после успешного повтора редактируется через `redactEvent`;
- три каскадных fallback-стратегии для агрегации реакций (`getRelation` → `relations.getChildEventsForEvent`
  → brute-force скан по всем таймлайнам) — прямое свидетельство, что более «правильные» пути в
  какой-то версии/состоянии SDK молча возвращали пусто в проде.

Автоматических ретраев и exponential backoff для исходящих сообщений в bastyon-chat **нет**.

### forta.chat

`SyncEngine` — **per-room FIFO** (не глобальный), до `MAX_CONCURRENT_ROOMS = 3` комнат параллельно,
захват операции — атомарная Dexie-транзакция на голову очереди комнаты (`claimDueOp`,
`sync-engine.ts:725`).

Явно закрытые классы отказов (это заметно сильнее, чем в bastyon-chat):

- **«таймаут, но сервер на самом деле принял»** — `isMessageAlreadyConfirmed()` (строка 1297) проверяет,
  не подхватило ли локальное сообщение серверный `eventId` через `/sync`-эхо, обогнавшее отказ SDK; если
  да — неудавшаяся операция тихо снимается вместо пометки «failed» (`WEE-40`);
- **гонка двух вкладок/устройств** — захват через одну `rw`-транзакцию + маркер `"syncing"` на комнату
  плюс идемпотентность на сервере через `clientId` как Matrix `txnId`;
- **зависший "syncing"-захват** после краша вкладки — снимается watchdog'ом (30 c) и стартовым снапшотом
  без увеличения счётчика ретраев (это не транспортная ошибка, а протухшая аренда);
- **Android WebView засыпает и пропускает событие `online`** — 30-секундный watchdog явно опрашивает
  `navigator.onLine` и форсит `setOnline(true)`, если движок всё ещё думает, что офлайн
  (`sync-engine.ts:443-450`) — задокументированный обход конкретного бага WebView, не догадка.

**Найденный архитектурный компромисс (не баг, а осознанный trade-off, задокументированный как
«hard invariant»):** так как очередь строго FIFO **по комнате**, если голова очереди застряла (например,
шифрование бросает `emptykey` из-за временно неполного набора ключей собеседника — см. раздел 6), **все**
последующие сообщения пользователя в этой же комнате ждут за ней до 5 ретраев × экспоненциальный бэкофф
(до 30 c каждый, то есть потенциально несколько минут) — и в UI нет явного индикатора «это сообщение не
отправляется, потому что впереди него застряло другое». На нестабильном Android-соединении это
реалистичный сценарий раздражения пользователя (сообщения «зависают» без объяснения).

## 6. E2E-шифрование — самый нетривиальный слой

**И bastyon-chat, и forta.chat не используют стандартный Matrix Olm/Megolm.** Обе реализации — это один
и тот же кастомный протокол на secp256k1-ключах блокчейна Bastyon/Pocketnet, почти дословно перенесённый
из `pcrypto.js` (1445 строк) в `matrix-crypto.ts`. Это значит, что **бо́льшая часть рисков и ограничений
одинакова в обоих приложениях** — это не регресс нового приложения, а унаследованная архитектура:

- 1:1-чаты: попарный ECDH → PBKDF2 → AES-SIV (`miscreant`), тело сообщения шифруется отдельно на
  каждого получателя.
- Групповые чаты: единый симметричный «common key», обёрнутый ECDH на каждого участника и
  опубликованный как **state-событие** `m.room.encryption` — то есть ключ группы виден (и
  перезаписываем) всем, у кого есть право писать state, и не имеет forward secrecy/ротации при выходе
  участника, кроме как через кэш-ключ на основе `usershash()` (хэш текущего состава).
- **Нет device verification, нет cross-signing, нет per-device Olm-сессий, нет key backup/recovery** — в
  обоих приложениях.

Это стоит явно зафиксировать: если у пользователя ожидание «настоящего» Matrix E2E (Olm/Megolm,
верификация устройств) — этого нет ни в старом, ни в новом приложении, и «починить» это в forta.chat
нельзя точечным фиксом, только переработкой протокола шифрования целиком (out of scope для «фикс, а не
рефакторинг ради рефакторинга», как явно указано в constraints проекта).

### Где forta.chat конкретно рискованнее bastyon-chat в этом слое

**Тихое исключение участника из шифрования при неполном наборе ключей.** И в 1:1, и в групповых чатах
проверка «готов ли пользователь к шифрованию» — `ui.keys.length >= m` (m = 12 производных ключей).
`entities/auth/model/stores.ts` (строки 493-503) содержит явный fallback-путь на случай, когда SDK
вернул **неполный** набор ключей (комментарий в коде: `filterXSS`-ошибка при очистке данных) — то есть
такое **уже случалось** в проде. Для 1:1-чата это безопасно ловится: `encryptEvent` бросает исключение
«No recipients with published keys», отправка блокируется явной ошибкой. Но в **групповом** пути
(`encryptEventGroup`/`getOrCreateCommonKey`) эквивалентной защиты нет: участник с неполным набором
ключей просто молча пропускается при обёртке common key (только `console.warn`), и получает сообщение,
которое не сможет расшифровать — без явного предупреждения отправителю о том, что кто-то из адресатов
исключён.

**Одна конкретная зафиксированная production-авария с шифрованием уже случилась и потребовала миграции
схемы.** `schema.ts`, версия v19 (строка ~856) документирует баг с коллизией ключа кэша `aeskeys` —
сообщения из-за него получали неверный производный AES-ключ, исчерпывали `MAX_ATTEMPTS=8` попыток
расшифровки в `DecryptionWorker` и навсегда застревали в терминальном статусе `"failed"` (который
намеренно никогда не пересматривается автоматически — чтобы не долбить бесконечно заведомо
нерасшифровываемый шифротекст). Потребовалась отдельная одноразовая миграция БД, чтобы дать этим
сообщениям второй шанс. Это прямое доказательство, что «сообщение навсегда застряло как [encrypted]» —
не гипотетический, а реальный инцидент.

### Что forta.chat уже делает лучше bastyon-chat в этом слое

- Расшифровка вынесена в Web Worker с различением «упала инфраструктура воркера» и «упала
  собственно крипто-операция» (`isWorkerInfraError`) — падение воркера не отравляет обработку
  сообщения, а откатывается на главный поток.
- Двухуровневый backoff в `DecryptionWorker` (быстрый: 2/5/10 c, медленный: 30 c/2 мин/10 мин/1 ч) —
  заметно тоньше, чем в bastyon-chat, где ретраев расшифровки в явном виде вообще нет (есть только
  проактивная инвалидация кэша ключа при ошибке, см. раздел 7).

## 7. Что стоит перенести из bastyon-chat — «дорого добытые» паттерны

Ниже — конкретные механизмы старого приложения, которые явно появились как реакция на реальный
продакшен-инцидент (видно по коду/комментариям), и которых **в forta.chat пока нет или нет в явном
виде**. Это самая практическая часть отчёта.

### R1. Идемпотентная запись вместо «throw on duplicate» в кэше, читаемом из реактивного пути

`chatstorage.js:202-208` содержит прямой комментарий разработчика:

> *«FIXME: It is not the best practice to use here put() instead of add(), but it solves vue.js
> repeating decryption requests as it doesn't throw Error on data update…»*

То есть: использование `add()` (бросает при дубликате ключа) в кэше расшифрованных сообщений вызывало
реальный баг — реактивность Vue переигрывала цикл «расшифровать → записать в кэш» так, что вторая
попытка записи натыкалась на исключение при дубликате, и это по цепочке приводило к бесконечным
повторным запросам расшифровки. Фикс — простая замена на идемпотентный `put()`.

**Применимость к forta.chat:** архитектурно `useLiveQuery` создаёт ровно тот же класс риска — реактивное
чтение из Dexie может спровоцировать повторную запись производного/кэш-состояния. **Нужно явно
проверить**, что все места, которые пишут производные/кэшируемые данные (не только оригинальные события)
в Dexie из реактивного пути, используют `put`/`bulkPut`, а не операции, бросающие на конфликте ключа.
Отдельно стоит прогнать по кодовой базе grep на использование `.add(` в `local-db/*-repository.ts` и
`event-writer.ts` и убедиться, что ни один из этих путей не достижим из UI-реактивности повторно для
одного и того же ключа.

### R2. Self-healing при поломке локальной БД вместо зависания

В bastyon-chat: если `IndexedDBStore.startup()` или `startClient()` падают — кэш токена авторизации
удаляется, следующий запуск идёт через чистый логин, а не пытается «починить» повреждённое хранилище на
месте (`mtrx.js:291-295, 309-311`).

**В forta.chat такого явного fallback-пути на случай, если сам Dexie не открывается/повреждён, не
обнаружено** (не проверялось построчно по всей `initChatDb`, но ни один из проанализированных файлов не
содержит catch-и-сбросить-локальную-БД сценария на уровне `ChatDatabase`/`initChatDb`). Учитывая, что
именно Android WebView — наиболее частый источник проблем с квотами/повреждением IndexedDB (что прямо
указано в описании проекта как зона боли), стоит явно добавить: при неудачном открытии/первом чтении
Dexie — не падать в неопределённое состояние, а инициировать управляемый ресинк с нуля (удалить локальную
БД пользователя и пересоздать её с явным UI-индикатором «синхронизация», а не тихим зависанием).

### R3. Дедуп + throttling уведомлений/звука

`notifier.js` в bastyon-chat:
- персистентный `{eventId: true}`-набор «уже показанных» уведомлений в localStorage — тот же ивент
  никогда не триггерит повторное уведомление, даже после перезагрузки/повторного синка backlog'а;
- звук/вибрация дросселируются максимум раз в 10 секунд по `localStorage["lastsounddate"]`.

Без этих двух механизмов реконнект с догоняющим синком по многим комнатам реалистично приводит к «шторму»
уведомлений/вибраций — по описанию это ровно тот класс симптомов («устройство как будто сломано»),
который упоминается в проекте. **Стоит явно проверить**, есть ли в `features/video-calls`/уведомлениях
forta.chat эквивалентный дедуп+throttling для push/локальных уведомлений при catch-up burst — если нет,
это дешёвый и локальный (не архитектурный) фикс.

### R4. Проактивная инвалидация кэша ключа при ошибке расшифровки

В `pcrypto.js` (`self.decrypt`, строки 529-556) — при ошибке расшифровки конкретный закэшированный
производный AES-ключ **сразу удаляется** из кэша, прежде чем исключение пробрасывается дальше: следующая
попытка гарантированно пересчитывает ключ с нуля, а не бьётся в тот же протухший/неверный кэш повторно.

**Применимость:** это прямо релевантно найденному в разделе 6 инциденту v19 (`aeskeys`-коллизия) —
поведение «удалить кэш при ошибке» снижает шанс, что одна коллизия кэш-ключа будет раз за разом
воспроизводить одну и ту же неверную расшифровку до полного исчерпания `MAX_ATTEMPTS`, вместо того чтобы
пересчитать с нуля хотя бы на одной из промежуточных попыток. Стоит проверить, делает ли
`DecryptionWorker`/`matrix-crypto.ts` в forta.chat аналогичную инвалидацию кэша конкретного ключа при
неудачной попытке, а не только глобальный ретрай с бэкоффом.

### R5. `M_USER_DEACTIVATED` как явный терминальный случай при логине

В bastyon-chat, пусть и реализовано хрупко (строковый матчинг вместо структурированного `errcode`), есть
явная развилка: если логин падает именно из-за деактивации аккаунта — приложение **не** проваливается
дальше в ветку «попробовать зарегистрироваться», которая для деактивированного аккаунта дала бы
непонятную ошибку. Стоит явно проверить (не проверялось в рамках этого аудита), обрабатывает ли
`connect-matrix-with-retry.ts`/логика логина в `entities/auth` этот конкретный `errcode` отдельно от
generic network-retry — если нет, деактивированный аккаунт может уходить в цикл ретраев вместо понятного
сообщения пользователю.

## 9. Что не является багом forta.chat, хотя выглядит тревожно

Чтобы отчёт не создавал ложного ощущения «всё сломано» — явно зафиксировать то, что при ближайшем
рассмотрении оказалось не хуже, а часто лучше, чем в bastyon-chat:

- Отсутствие Olm/Megolm и device verification — **унаследованная особенность обоих приложений**, не
  регресс форты.
- Транзакционность записи (`EventWriter`), FIFO-очередь с идемпотентными txnId, обработка «таймаут, но
  сервер принял» (`isMessageAlreadyConfirmed`) — всё это **отсутствует** в bastyon-chat вовсе и является
  чистым улучшением в forta.chat.
- Схема Dexie (`schema.ts`) — 19 версий, каждая с задокументированной причиной миграции, в основном
  идемпотентные и самоограниченные — дисциплина заметно выше, чем в bastyon-chat (там миграции — это
  просто снос localStorage-ключей).
- Тестовое покрытие протокольного слоя в forta.chat практически отсутствует как класс в bastyon-chat
  (там тестов нет вообще).

### 11.1. Исправлено

| Находка | Уверенность | Что сделано |
|---|---|---|
| **Состояние шифрования комнаты не обновляется при изменении состава участников** — новый участник группы может быть навсегда и молча исключён из будущих сообщений | **[ПОДТВЕРЖДЕНО]** трассировкой полного пути `RoomMember.membership` → `onMembership` → `checkPeerKeys` | `checkPeerKeys()` (`entities/chat/model/chat-store.ts`) читает только `roomCrypto.canBeEncrypt()`, который читает уже закэшированные `users`/`usersinfo` — эти поля обновляются ТОЛЬКО внутри `prepare()`, а `onMembership` (`entities/auth/model/stores.ts`) вызывал `checkPeerKeys` напрямую, без `prepare()`. Поскольку `usershash()` (определяющий, какой common-key-event использовать в группе) считается от того же устаревшего `usersinfo`, `getOrCreateCommonKey()` продолжал находить и переиспользовать **старый** ключ, никогда не обёрнутый для нового участника — тот получает сообщения, которые никогда не сможет расшифровать, без единой ошибки у отправителя. Исправлено: `onMembership` теперь вызывает `roomCrypto.prepare()` (без force — `getusershistory()` синхронна и локальна, RPC для нового участника всё равно уйдёт) **перед** `checkPeerKeys`. Тест: `entities/chat/model/__tests__/chat-store-check-peer-keys.test.ts` |
| **«Переход к сообщению» (поиск, цитата, старое закреплённое) не работает для всего, что вне уже загруженного «хвоста» сообщений** | **[ПОДТВЕРЖДЕНО]** трассировкой `enterDetachedMode` → `activeMessages` → `use-scroll-to-message.ts` | В штатном режиме (`chatDbKitRef.value` установлен) `activeMessages` всегда читает `dexieMessages` (Dexie live query «последние N сообщений», без якоря). `enterDetachedMode()` пишет context-снэпшот только в legacy-ref `messages.value[roomId]`, который в этом режиме никто не читает — переход к старому сообщению либо скроллит в случайную позицию (по индексу из отброшенного контекста, применённому к неизменному «хвосту»), либо после 3 попыток показывает тост «не удалось перейти». Исправлено: `activeMessages` теперь ветвится по `isDetachedFromLatest` — в detached-режиме читает `messages.value[roomId]` (куда пишет `enterDetachedMode`), иначе — как раньше, `dexieMessages`. `exitDetachedMode()` уже корректно сбрасывает флаг и перезагружает live-данные. **Дополнительно найден и исправлен тонкий баг мемоизации**, обнаруженный только при написании regression-теста: fast-path кэш (`_prevActiveOutput`) в конце функции перезаписывается независимо от того, какая ветка сработала, поэтому при выходе из detached-режима кэш оставался «заражён» detached-снэпшотом и подменял собой свежие live-данные даже после корректного возврата в live-ветку — потребовалась явная инвалидация `_prevDexieInput` при входе в detached-ветку. Тесты: `entities/chat/model/chat-store-enter-detached-mode.test.ts` |

### 11.2. Проверено и сознательно НЕ исправлено
